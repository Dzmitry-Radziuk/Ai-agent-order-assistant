# AGENTS.md — рабочий контракт проекта

Этот файл обязателен для любого AI-агента и разработчика, который меняет проект.

Он задаёт порядок восстановления контекста, анализа системы, безопасной разработки,
архитектурных изменений и проверки результата.

Главная цель — не просто заставить конкретный пример пройти тест, а сохранить
корректность, понятность и управляемость системы в целом.

Текущий код и Git-состояние всегда важнее ранее сохранённого описания.


## 1. Начало каждой задачи

До анализа или изменения кода:

1. Убедиться, что рабочий каталог — корень этого репозитория.

2. Выполнить:

   `python scripts/build_agent_context.py`

   и прочитать:

   `.agents/runtime/CURRENT_CONTEXT.md`

3. Прочитать:

   - `.agents/PROJECT_MAP.md`
   - `.agents/DEVELOPMENT_PROCESS.md`
   - `.agents/DECISIONS.md`

4. Проверить:

   - `git status --short --branch`;
   - текущую ветку;
   - последний commit;
   - весь существующий diff в файлах задачи.

5. Считать незакоммиченные изменения собственностью пользователя.

   Не удалять, не форматировать и не переписывать их без прямой необходимости.

6. Найти реальный путь выполнения сценария от входа до внешнего эффекта и прочитать
   затронутые файлы полностью.

   Снимок контекста помогает навигации, но не заменяет чтение кода.

7. До изменения кода сформировать модель выполнения текущего сценария:

   `вход → нормализация → маршрутизация → state → бизнес-логика → persistence → внешний эффект`

   Для каждого этапа определить, какой модуль является владельцем поведения.

8. Проверить callers и callees изменяемых функций, а также все места,
   использующие соответствующие:

   - `Intent`;
   - state;
   - `ParsedCommand`;
   - callback;
   - сервис;
   - repository;
   - внешний adapter.

9. Если локальный снимок контекста не соответствует рабочему дереву, сначала
   обновить его.

   Проверка без перезаписи:

   `python scripts/build_agent_context.py --check`


### 1.1. Обязательная передача контекста

В начале каждой задачи после прочтения `AGENTS.md` обязательно прочитать
`PROJECT_HANDOFF.md` в корне репозитория.

До изменения кода сверить текущую задачу с разделами `Текущая задача`,
`Критические архитектурные правила`, `Что сейчас работает` и `Что не работает /
открытые проблемы`. Фактический код и текущий Git-diff имеют приоритет над
устаревшей записью handoff.

В конце каждой задачи обновить `PROJECT_HANDOFF.md`, если были изменения кода,
новая ошибка, архитектурное решение, изменение pipeline, изменения тестов,
важное подтверждённое поведение или незавершённая работа. Устаревшие сведения
заменять, а не накапливать в виде журнала.

В handoff явно разделять подтверждённые факты, предположения и то, что ещё нужно
проверить. Не записывать секреты, токены, пароли, ключи и webhook credentials.
Задача не считается завершённой, пока handoff соответствует фактическому
состоянию проекта.



## 2. Источники истины

При конфликте использовать следующий приоритет:

1. Явное текущее требование пользователя.
2. Исполняемый код, миграции и тесты текущей ветки.
3. `.agents/DECISIONS.md` для подтверждённых продуктовых и архитектурных решений.
4. `docs/user-scenarios/scenarios.json` для пользовательских сценариев и связей с тестами.
5. `README.md`, `README-DEVOPS.md`, `docs/` и `.agents/PROJECT_MAP.md`.
6. Предыдущие сообщения, логи и локальные снимки.

Документация не подтверждает поведение сама по себе.

Значимые утверждения необходимо сверять с исполняемым кодом или целевым тестом.


## 3. Неприкосновенные границы

- Не менять `.gitlab-ci.yml`, `.gitlab/`, `docker/`, `docker-compose.yml`,
  `Dockerfile`, `README-DEVOPS.md` и серверные worker-настройки без отдельного
  прямого запроса.

  Это зона DevOps-контракта.

- Не менять секреты, GitLab Variables, webhook, внешние таблицы,
  Telegram Bot API, production и central Apps Script без явного разрешения.

- Не отправлять реальные заявки и не включать
  `GOOGLE_ORDER_SUBMISSION_ENABLED=true`
  во время обычной локальной разработки.

- Не выполнять:

  - `git reset --hard`;
  - `git checkout --`;
  - force push;
  - удаление volumes;
  - другие необратимые действия.

- Не выводить в чат или логи:

  - `.env`;
  - service-account JSON;
  - токены;
  - пароли;
  - API-ключи;
  - полные строки подключения.

- Не делать commit, merge, push, deploy, регистрацию webhook или публичный туннель,
  если пользователь не попросил именно это действие.


## 4. Ключевые инварианты поведения

Следующие свойства системы нельзя нарушать локальным исправлением или новым
функционалом.

- Telegram update принимается идемпотентно:
  повторная доставка не должна повторять бизнес-эффект.

- Изменения одного чата сериализуются.

- Разные заведения изолируются по своей таблице и своему состоянию.

- Доступ проверяется через центральный реестр заведений и локальную привязку.

- Снятый доступ нельзя обойти старым invite-кодом.

- Неуверенное или категорийное совпадение товара нельзя автоматически подставлять
  как точный товар.

  Пользователь выбирает из вариантов или уточняет название.

- Текст, голос и фото должны приводить к одной безопасной state-machine логике.

- Свободная человеческая фраза не должна обходить проверки текущего состояния.

- Callback со старой ревизией интерфейса не может менять текущий черновик.

- Количество и комментарии сохраняются для правильной позиции.

- Общий комментарий применяется ко всем относящимся позициям ровно один раз.

- При выключенной внешней отправке подтверждение всё равно записывает данные
  в лист заказа заведения, запускает пересчёт и завершает черновик,
  но не вызывает центральную отправку.

- Статусы читаются из реального листа истории текущего заведения и не изменяют таблицу.

- Запрос на ненайденный товар сохраняется через отдельный сценарий добавления товара,
  не маскируясь похожей позицией.

Подробные пути реализации перечислены в `.agents/PROJECT_MAP.md`.


## 5. Архитектурное мышление перед изменением кода

Цель агента — не только исправить конкретный пользовательский пример,
а сохранить и по возможности упростить поведение системы в целом.

Перед внесением изменений необходимо определить:

1. Какой пользовательский сценарий затронут полностью:
   от Telegram update до изменения state, ответа пользователю и внешнего эффекта.

2. Где находится естественный источник решения:

   - state machine;
   - intent routing;
   - deterministic parser;
   - AI parser;
   - AI postprocessing;
   - product matching;
   - business service;
   - persistence;
   - Telegram transport;
   - infrastructure.

3. Является ли наблюдаемая ошибка:

   - локальным багом;
   - отсутствующим продуктовым сценарием;
   - неправильной маршрутизацией;
   - неправильной ответственностью слоя;
   - дублированием бизнес-правила;
   - накопленным архитектурным долгом.

4. Не существует ли уже аналогичного правила в другом месте системы.

5. Не приведёт ли исправление к появлению ещё одного независимого источника
   одного и того же бизнес-правила.

6. Можно ли решить проблему изменением существующей модели,
   вместо добавления нового исключения поверх результата.


### 5.1. Запрет на автоматическое наращивание защитных правил

Нельзя автоматически считать добавление нового:

- `if`;
- `elif`;
- regex;
- guard;
- fallback;
- postprocessing;
- специального исключения;
- повторной нормализации;
- дополнительной проверки после AI;

правильным решением.

Перед добавлением такого правила агент обязан определить,
почему существующие уровни системы не могут решить проблему на своём естественном уровне.

Если новый guard нужен только потому, что предыдущий этап регулярно возвращает
неправильную структуру, сначала необходимо проверить возможность исправить
предыдущий этап.


### 5.2. Предпочитаемые решения

Предпочитать:

- исправление правила в одном ответственном слое;
- единый источник истины;
- устранение дублирующей логики;
- явную state-machine модель вместо набора специальных проверок;
- расширение существующей абстракции вместо создания параллельного механизма;
- нормализацию данных один раз в определённой точке;
- исправление причины неправильного результата, а не последующую цепочку его коррекций.


### 5.3. Минимальный diff не является самоцелью

Для локального бага в корректной архитектуре предпочтительно небольшое изменение.

Но минимальное количество изменённых строк или файлов не является самостоятельной
целью.

Нужно менять минимально необходимую область системы.

Если корректное решение требует:

- изменения границы модулей;
- выделения отдельной ответственности;
- декомпозиции перегруженного компонента;
- устранения дублирования;
- изменения внутреннего контракта;

это допустимо после анализа зависимостей и существующих тестов.

Не выбирать заведомо более хрупкое решение только потому,
что оно изменяет меньше строк.


### 5.4. Тест не заменяет архитектурное решение

Прохождение нового теста не доказывает корректность решения само по себе.

Запрещено считать задачу решённой по схеме:

`новый пример → новый if/regex → новый тест → готово`

без анализа соседних сценариев.

Тест должен подтверждать выбранное решение, а не определять архитектуру системы.


## 6. Архитектурный долг и декомпозиция

Большой файл сам по себе не является причиной рефакторинга.

Причиной для декомпозиции считается:

- смешение нескольких ответственностей;
- высокая связанность;
- наличие нескольких независимых этапов обработки;
- необходимость добавлять специальные проверки в разные части одного пайплайна;
- большое количество неявно связанных функций;
- зависимость корректности от точного порядка множества postprocessing-операций;
- повторение одного бизнес-правила в разных местах.


### 6.1. Перед расширением сложного модуля

Если текущая задача требует изменения крупного или сложного модуля,
агент должен проверить:

- какие независимые обязанности выполняет модуль;
- какие части относятся к parsing;
- какие к routing;
- какие к state;
- какие к business rules;
- какие к postprocessing;
- какие к persistence;
- какие к transport;
- какие функции координируют большое количество независимых преобразований;
- повторяются ли правила;
- зависит ли результат от скрытых побочных эффектов;
- требуется ли для нового поведения менять несколько несвязанных частей одного файла.


### 6.2. Поведенчески нейтральная декомпозиция

Если структура мешает безопасно реализовать текущую задачу,
разрешается сначала провести поведенчески нейтральную декомпозицию.

При такой декомпозиции:

1. Не менять публичное пользовательское поведение.
2. Не менять одновременно архитектуру и бизнес-правила без необходимости.
3. Переносить существующую логику максимально механически.
4. Сохранять публичные интерфейсы там, где это разумно.
5. Не переписывать одновременно алгоритмы, которые можно сначала просто перенести.
6. После каждого логического этапа запускать существующие тесты.
7. Только после подтверждения эквивалентного поведения добавлять новый функционал.

Не смешивать большую декомпозицию и изменение бизнес-поведения
в один непроверяемый шаг.


### 6.3. Размер и ответственность файлов

Не существует жёсткого ограничения по количеству строк.

Однако файл следует считать кандидатом на декомпозицию,
если для понимания одного пользовательского сценария необходимо удерживать
в голове несколько независимых подсистем.

При декомпозиции группировать код по ответственности,
а не просто делить большой файл на несколько файлов одинакового размера.


## 7. Правило изменения кода

Для каждого исправления или нового функционала:

1. Зафиксировать наблюдаемое поведение:

   - пользовательское сообщение;
   - `update_id`;
   - текущее состояние;
   - лог;
   - callback;
   - воспроизводящий тест.

2. Найти первый неверный переход.

   Не исправлять только финальный текст или последний симптом,
   если ошибка возникла раньше.

3. Проверить соседние маршруты:

   - text;
   - voice;
   - photo;
   - callback;
   - повтор Celery;
   - восстановление после сбоя;
   - переход между состояниями.

4. Определить правильный слой исправления до изменения кода.

5. Проверить, можно ли удалить или объединить существующее специальное правило
   вместо добавления ещё одного.

6. Менять минимально необходимую область системы,
   а не минимально возможное количество строк или файлов.

7. Не проводить несвязанный с задачей рефакторинг.

   При этом рефакторинг, необходимый для корректной реализации текущей задачи,
   не считается попутным.

8. Если одна бизнес-сущность или правило последовательно обрабатывается
   в нескольких местах, считать это сигналом возможного нарушения ответственности.

9. Добавить минимальный регрессионный тест на пользовательский сценарий
   и отрицательный тест против неправильной маршрутизации.

10. Сохранять UX-контракт, если его изменение не является частью задачи:

    - текст;
    - HTML;
    - emoji;
    - порядок кнопок;
    - callback data;
    - состояние.

11. Выполнить проверки из `.agents/DEVELOPMENT_PROCESS.md`
    пропорционально риску изменения.

12. Обновить сценарии или документацию,
    если изменилось видимое поведение или эксплуатационный контракт.

13. Повторно создать снимок контекста.

14. Проверить итоговый diff целиком, а не только изменённый фрагмент.


### 7.1. Если количество специальных условий увеличилось

Если после изменения стало больше:

- специальных `if`;
- regex;
- fallback;
- исключений;
- postprocessing-шагов;
- отдельных обработчиков одного и того же понятия;

агент обязан перед завершением задачи объяснить:

1. почему новое правило необходимо;
2. почему проблема не должна решаться в существующем ответственном слое;
3. почему объединение с существующим правилом хуже;
4. какие соседние сценарии защищены тестами.

Если убедительного объяснения нет,
нужно пересмотреть архитектурное решение.


## 8. Intent и state-machine

Intent не является самостоятельной командой вне контекста.

При изменении intent routing необходимо учитывать текущее состояние пользователя.

Перед добавлением нового intent агент должен определить:

1. Для чего нужен отдельный intent.
2. В каких состояниях он допустим.
3. В каких состояниях он запрещён.
4. Какие существующие intent семантически наиболее близки к нему.
5. Какие пользовательские формулировки могут быть ошибочно направлены в соседние intent.
6. Как intent работает для текста и голоса.
7. Может ли аналогичная фраза обозначать товар в сценарии создания заявки.
8. Нужно ли вообще добавлять новый intent или сценарий лучше выразить существующей
   state-machine логикой.

Нельзя добавлять новый intent только потому,
что появилась одна новая пользовательская фраза.

Один intent должен отражать отдельное намерение пользователя,
а не отдельную формулировку одного намерения.


## 9. Матрица естественных текстовых и голосовых формулировок

Любая новая команда, intent, кнопка или изменение состояния диалога обязаны
проверяться не только по одной тестовой фразе.

До завершения задачи необходимо составить матрицу естественных вариантов,
которые может использовать человек.

Минимально проверить:

- короткую команду;
- вежливую просьбу;
- разговорную форму;
- вопросительную форму;
- варианты рода;
- варианты числа;
- варианты падежа;
- лишние слова;
- приветствие перед командой;
- слова-паразиты;
- знаки препинания;
- результат после voice transcription;
- неоднозначную формулировку.

Для каждого intent нужны:

- несколько положительных вариантов;
- отрицательные варианты;
- примеры соседних intent;
- примеры, которые должны остаться `unknown`;
- примеры, которые являются названием товара, а не командой.

Проверять одну и ту же матрицу:

- для текста;
- для голоса;
- в каждом релевантном state.

Например:

- пустая заявка;
- заполненный черновик;
- карточка уточнения;
- ввод количества;
- review;
- финальное подтверждение;
- просмотр истории.

Новая фраза не должна ломать маршруты соседних команд.

Сначала фиксируется ожидаемая семантика и intent,
после этого добавляются регрессионные тесты.


## 10. AI и deterministic logic

AI не является единственным источником истины для структуры команды.

Постоянный принцип: AI предлагает и интерпретирует, исходная фраза подтверждает,
каталог уточняет, детерминированный код выполняет действие. AI payload не
переписывает подтверждённые source/catalog факты о количестве заказа, товаре,
поставщике, заведении или опасной мутации.

Если deterministic parser может надёжно определить факт,
не нужно заставлять AI угадывать его без необходимости.

При этом запрещено создавать бесконечную цепочку:

`AI → исправление → исправление исправления → fallback → ещё один guard`

без явной ответственности каждого этапа.

Для каждого postprocessing-шага должно быть понятно:

- какую конкретную ошибку входных данных он исправляет;
- почему эту ошибку нельзя устранить раньше;
- какие данные считаются входным контрактом;
- какой контракт гарантируется на выходе;
- какие тесты подтверждают это правило.

Если несколько postprocessing-функций исправляют одно и то же понятие,
необходимо рассмотреть их объединение или изменение границы слоя.


## 11. Поиск и сопоставление товаров

Название, количество, единица измерения, фасовка, поставщик и комментарий —
разные понятия.

Не смешивать их без явного правила.

При сопоставлении товара:

- не превращать сомнительное совпадение в точное;
- не добавлять характеристики, которых пользователь не называл;
- не терять явно названные характеристики;
- не принимать диапазон фасовки за количество заказа;
- не принимать комментарий за отдельный товар;
- не принимать навигационную фразу за товар;
- не переносить комментарий на другую позицию без подтверждённой связи.

Если AI и deterministic parser расходятся,
необходимо определить, какой источник авторитетен для конкретного поля,
а не выбирать один источник целиком для всей команды.


## 12. Состояние и побочные эффекты

Изменение состояния и внешний эффект необходимо рассматривать отдельно.

При работе со сценарием проверить:

- когда сохраняется state;
- когда создаётся checkpoint;
- когда отправляется Telegram reply;
- когда выполняется запись в Google Sheets;
- когда выполняется центральная отправка;
- что происходит при исключении между этими этапами;
- что происходит при повторной доставке update;
- что увидит пользователь после восстановления.

Не считать сценарий успешным только потому,
что внутреннее состояние изменилось.

Не считать внешний вызов безопасным только потому,
что используется idempotency на входном update.


## 13. Ошибки внешних сервисов

Telegram, OpenAI, Google Sheets, Redis, Celery, proxy и другие внешние системы
могут быть временно недоступны.

При обработке ошибки необходимо различать:

- бизнес-ошибку;
- ошибку пользователя;
- временную транспортную ошибку;
- таймаут;
- повторную доставку;
- ошибку внешнего API;
- недоступность инфраструктуры.

Не пытаться исправлять инфраструктурную ошибку изменением intent/parser/state-machine,
если причина находится в transport или infrastructure слое.


## 14. Стиль проекта

- Python 3.12+.
- Строгая типизация.
- Ruff и mypy согласно `pyproject.toml`.
- Короткие однострочные docstring на русском обязательны для:
  - функций;
  - методов;
  - классов;
  - тестов.

- Пользовательские тексты пишутся для повара или сотрудника кафе:
  простые слова, одно действие за раз, без внутренних терминов.

- Логи структурированные.

- Пользовательский контент не логируется открыто при:

  `LOG_USER_CONTENT=false`

- Не добавлять комментарии, которые просто пересказывают очевидную строку кода.

- Комментарий должен объяснять причину, ограничение или неочевидный инвариант.

- Имена функций и модулей должны отражать ответственность,
  а не конкретный баг, ради которого они были созданы.

Плохо:

`fix_parmesan_query()`

Лучше:

`parse_history_search_query()`


## 15. Git

Перед изменением обязательно проверить текущий diff.

Не перезаписывать пользовательские изменения.

Не смешивать в одном изменении:

- функциональную задачу;
- массовое форматирование;
- несвязанный cleanup;
- случайное обновление зависимостей.

Commit выполняется только по прямому запросу пользователя.

Комментарий commit — на русском, от первого лица и в прошедшем времени.

Примеры:

- `Поправил маршрутизацию поиска по истории`
- `Добавил поиск товара в прошлых заявках`
- `Разделил постобработку ответов OpenAI по ответственности`


## 16. Проверки

Набор проверок определяется риском задачи.

Минимально:

- целевые тесты;
- связанные regression tests;
- Ruff;
- `git diff --check`.

Для изменений:

- intent;
- state-machine;
- parser;
- matching;
- postprocessing;
- persistence;

обязательно запускать соседние сценарии,
а не только новый тест.

После архитектурного переноса сначала подтвердить,
что старые тесты проходят без изменения ожидаемого поведения.

После этого добавлять новое поведение.


## 17. Готовность результата

Работа считается завершённой только если:

- понятна причина проблемы;
- понятен изменённый маршрут;
- изменение находится в ответственном слое;
- исправлена причина, а не только один конкретный пример;
- не создан новый параллельный источник бизнес-правил без необходимости;
- итоговое решение не увеличивает архитектурную сложность без явного обоснования;
- добавлены или обновлены релевантные тесты;
- проверены отрицательные сценарии;
- проверены соседние intent/state;
- целевые и обязательные проверки прошли;
- `git diff --check` не нашёл ошибок;
- существующие пользовательские изменения сохранены;
- нет секретов;
- нет случайных артефактов;
- нет лишних файлов;
- документация и сценарии соответствуют коду;
- выполнены только разрешённые внешние действия.

## 18. Долговременные архитектурные правила

Каналы ввода являются adapters, а не владельцами бизнес-логики. Telegram Bot,
Mini App, MAX и Web должны использовать общее прикладное ядро без копирования
use cases. История и свободные semantic queries будут отдельным use case, но не
реализуются автоматически в текущем блоке.

Перед переносом, слиянием, разделением или удалением выполняется полный
repository-wide usage/duplicate/dead-code audit до и после изменения. Один
owner отвечает за одну responsibility; facade допустим только как простой
re-export при подтверждённых callers. Подробный процесс закреплён в
`.agents/DEVELOPMENT_PROCESS.md`, а долговременные решения — в
`.agents/DECISIONS.md`.

Если после изменения количество специальных условий увеличилось,
в итоговом отчёте отдельно объяснить почему.

Если остался известный архитектурный риск,
не скрывать его за зелёными тестами.


## 18. Формат итогового сообщения агента

После выполнения задачи кратко сообщить:

1. Что было причиной.
2. Что изменено.
3. Почему выбран именно этот уровень системы.
4. Какие проверки выполнены.
5. Какие соседние сценарии проверены.
6. Остались ли риски или технический долг.

Не перечислять десятки внутренних деталей,
если они не помогают понять результат.

Не говорить «всё исправлено» только на основании одного успешного теста.


## 19. Главное правило

Не оптимизировать проект под отдельные тестовые фразы.

Не лечить каждый новый пользовательский пример очередным исключением.

Сначала понять:

`какой слой должен владеть этим поведением`

и только потом менять код.

Предпочтительный порядок работы:

`понять систему → найти источник проблемы → выбрать правильную границу → изменить код → проверить соседние сценарии → подтвердить результат тестами`

а не:

`получить пример → добавить if → добавить тест → перейти к следующему примеру`.
