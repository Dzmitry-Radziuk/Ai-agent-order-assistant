# AGENTS.md — рабочий контракт проекта

Этот файл обязателен для любого AI-агента и разработчика, который меняет проект. Он задаёт порядок восстановления контекста, безопасной разработки и проверки результата. Текущий код и Git-состояние всегда важнее ранее сохранённого описания.

## 1. Начало каждой задачи

До анализа или изменения кода:

1. Убедиться, что рабочий каталог — корень этого репозитория.
2. Выполнить `python scripts/build_agent_context.py` и прочитать `.agents/runtime/CURRENT_CONTEXT.md`.
3. Прочитать `.agents/PROJECT_MAP.md`, `.agents/DEVELOPMENT_PROCESS.md` и `.agents/DECISIONS.md`.
4. Проверить `git status --short --branch`, текущую ветку, последний commit и весь существующий diff в файлах задачи.
5. Считать незакоммиченные изменения собственностью пользователя. Не удалять, не форматировать и не переписывать их без прямой необходимости.
6. Найти реальный путь выполнения сценария от входа до внешнего эффекта и прочитать затронутые файлы полностью. Снимок контекста помогает навигации, но не заменяет чтение кода.

Если локальный снимок не совпадает с рабочим деревом, сначала обновить его. Проверка без перезаписи: `python scripts/build_agent_context.py --check`.

## 2. Источники истины

При конфликте использовать следующий приоритет:

1. Явное текущее требование пользователя.
2. Исполняемый код, миграции и тесты текущей ветки.
3. `.agents/DECISIONS.md` для подтверждённых продуктовых и архитектурных решений.
4. `docs/user-scenarios/scenarios.json` для пользовательских сценариев и связей с тестами.
5. `README.md`, `README-DEVOPS.md`, `docs/` и `.agents/PROJECT_MAP.md`.
6. Предыдущие сообщения, логи и локальные снимки.

Документация не подтверждает поведение сама по себе: значимые утверждения сверяются с кодом или целевым тестом.

## 3. Неприкосновенные границы

- Не менять `.gitlab-ci.yml`, `.gitlab/`, `docker/`, `docker-compose.yml`, `Dockerfile`, `README-DEVOPS.md` и серверные worker-настройки без отдельного прямого запроса. Это зона DevOps-контракта.
- Не менять секреты, GitLab Variables, webhook, внешние таблицы, Telegram Bot API, production и central Apps Script без явного разрешения.
- Не отправлять заявки и не включать `GOOGLE_ORDER_SUBMISSION_ENABLED=true` во время обычной локальной разработки.
- Не выполнять `git reset --hard`, `git checkout --`, force push, удаление volumes или другие необратимые действия.
- Не выводить в чат или логи `.env`, service-account JSON, токены, пароли и полные строки подключения.
- Не делать commit, merge, push, deploy, регистрацию webhook или публичный туннель, если пользователь не попросил именно это действие.

## 4. Ключевые инварианты поведения

- Telegram update принимается идемпотентно: повторная доставка не должна повторять бизнес-эффект.
- Изменения одного чата сериализуются; разные заведения изолируются по своей таблице.
- Доступ проверяется через центральный реестр заведений и локальную привязку. Снятый доступ нельзя обойти старым invite-кодом.
- Неуверенное или категорийное совпадение товара нельзя автоматически подставлять как точный товар. Пользователь выбирает из вариантов или уточняет название.
- Текст, голос и фото должны приводить к одной безопасной state-machine логике. Свободная человеческая фраза не должна обходить проверки состояния.
- Callback со старой ревизией интерфейса не может менять текущий черновик.
- Количество и комментарии сохраняются для правильной позиции; общий комментарий применяется ко всем относящимся позициям ровно один раз.
- При выключенной внешней отправке подтверждение всё равно записывает данные в лист заказа заведения, запускает пересчёт и завершает черновик, но не вызывает центральную отправку.
- Статусы читаются из реального листа истории текущего заведения и не изменяют таблицу.
- Запрос на ненайденный товар сохраняется через отдельный сценарий добавления товара, не маскируясь похожей позицией.

Подробные пути реализации перечислены в `.agents/PROJECT_MAP.md`.

## 5. Правило изменения кода

Для каждого исправления:

1. Зафиксировать наблюдаемое поведение: сообщение, update_id, состояние, лог или воспроизводящий тест.
2. Найти первый неверный переход, а не исправлять только финальный текст.
3. Проверить соседние маршруты: text, voice, photo, callback, повтор Celery и восстановление после сбоя.
4. Добавить минимальный регрессионный тест на пользовательскую фразу и отрицательный тест против неправильной маршрутизации.
5. Менять минимальный набор файлов. Не проводить попутный рефакторинг.
6. Сохранять точный UX-контракт: текст, HTML, emoji, порядок кнопок, callback data и состояние.
7. Выполнить проверки из `.agents/DEVELOPMENT_PROCESS.md` пропорционально риску.
8. Обновить сценарии или документацию, если изменилось видимое поведение или эксплуатационный контракт.
9. Повторно создать снимок контекста и проверить итоговый diff.

## 6. Стиль проекта

- Python 3.12+, строгая типизация, Ruff и mypy согласно `pyproject.toml`.
- Короткие однострочные docstring на русском обязательны для функций, методов, классов и тестов.
- Пользовательские тексты пишутся для повара или сотрудника кафе: простые слова, одно действие за раз, без внутренних терминов.
- Логи структурированные. Пользовательский контент не логируется открыто при `LOG_USER_CONTENT=false`.
- Комментарий commit — на русском, от первого лица и в прошедшем времени: `Поправил ...`, `Добавил ...`.

## 7. Готовность результата

Работа завершена, только если:

- причина и изменённый маршрут понятны;
- добавлены или обновлены релевантные тесты;
- целевые и обязательные проверки прошли;
- `git diff --check` не нашёл ошибок;
- существующие пользовательские изменения сохранены;
- нет секретов, случайных артефактов и лишних файлов;
- документация и сценарии соответствуют коду;
- выполнены только разрешённые внешние действия;
- в итоговом сообщении перечислены результат, проверки и оставшиеся риски.
