# Процесс разработки

```powershell
Set-Location C:\Users\Dzmitry\Desktop\python_project_n8n\restaurant_bot_python\restaurant_bot_python
.\.venv\Scripts\python.exe scripts\build_agent_context.py
Get-Content .agents\runtime\CURRENT_CONTEXT.md

```

После этого прочитать целиком затронутые исходники, их тесты и существующий diff. Нельзя начинать исправление только по скриншоту, если доступны код и логи.

## 2. Классификация задачи

| Тип | Обязательное исследование |
|---|---|
| Ошибка маршрутизации | Telegram event → normalizer → parser/AI → orchestrator → engine → reply |
| Ошибка товара | Исходная фраза → AI payload → matching → candidate resolution → состояние позиции |
| Количество/единица | Парсер → нормализация единиц → состояние текущей проблемы → кратность/остаток → финальная проверка |
| Комментарий | AI payload → local/global comment → дедупликация → submission row |
| Запись заявки | Engine guard → pending submission → checkpoints → Google Sheets → пересчёт → ответ |
| Статус заявки | Привязка заведения → history read → фильтрация → группировка → пагинация |
| Доступ | Центральный реестр → кэш → venue binding → context → повторная проверка перед внешним эффектом |
| Инфраструктура | Только чтение DevOps-контракта, пока пользователь явно не разрешил изменение |

## 3. Диагностика

1. Получить точное время, update_id/chat hash, тип входа и ожидаемый результат.
2. Найти в структурированных логах последовательность событий одного update.
3. Отделить распознавание от маршрутизации: корректная транскрипция ещё не означает корректный intent.
4. Зафиксировать состояние до и после engine transition.
5. Определить первый слой, где данные стали неверными.
6. Создать минимальный воспроизводящий тест до исправления.
7. Проверить отрицательный пример: похожая, но другая фраза не должна пойти по новому маршруту.

Логи читаются с ограниченным временным окном и фильтром. Нельзя печатать весь environment или секреты.

Для каждого инцидента сначала фиксируется первый доказанный неверный этап:
`input → normalization → parsing → reconciliation → routing → state → persistence → external effect`.
Если причина не подтверждена тестом или логом, сначала выполняется диагностика,
а не добавляется новый guard или fallback.

## 4. Проектирование изменения

Перед правкой сформулировать:

- пользовательское правило простыми словами;
- текущий ошибочный переход;
- новый переход и безопасный fallback;
- состояние, которое разрешено менять;
- соседние сценарии, которые нельзя затронуть;
- тесты, доказывающие корректность и отсутствие ложной маршрутизации.

AI используется для понимания разнообразной речи, но авторизация, навигация, отрицание, подтверждение, выбор кандидата и внешние эффекты должны иметь детерминированные guards.

## 5. Реализация

1. Менять минимальный слой, в котором возникла причина.
2. Не дублировать словари фраз в нескольких модулях без необходимости.
3. Не связывать бизнес-логику с конкретным текстом кнопки: callback/intent остаётся стабильным при UX-правке.
4. Не подменять отсутствующий товар семантически родственным товаром.
5. Не менять первую позицию по умолчанию, если цель голосовой команды неоднозначна.
6. Любой внешний эффект делать идемпотентным и защищённым повторной проверкой доступа.
7. Для новой настройки добавить тип, валидацию, безопасное значение в `.env.example`, документацию и тест.
8. Для изменения БД создать Alembic migration и вручную проверить upgrade; существующие миграции не переписывать.

Перед архитектурным переносом выполняется repository-wide audit для каждого
затрагиваемого symbol: production/test callers, aliases, re-exports,
dynamic/framework callers, похожие реализации и dead code. После переноса
проверяется тот же список. Один behavior/responsibility должен иметь одного
implementation owner; facade допустим только как простой re-export при
подтверждённых callers.

Пакет `services/` считается transitional compatibility layer, а не целевой
архитектурой. Его core-ответственности переносятся по одному доказанному seam;
оставшийся facade не содержит алгоритма и сохраняется только при подтверждённых
callers и понятном пути удаления.

Внешние адаптеры `api/`, `workers/` и channel integrations находятся на внешнем
слое. Application/orchestration-код зависит только от application-портов и не
импортирует конкретные worker-задачи или другие внешние delivery adapters.
Адаптеры могут импортировать application use cases и реализовывать их порты.

Большие функции и файлы разделяются только по реальным ответственностям и
стадиям. Нельзя переносить монолит целиком или создавать `helpers.py`,
`utils.py`, `common.py` и бессмысленные микромодули.

Класс, mixin, Protocol или интерфейс создаётся только при наличии реального
состояния, жизненного цикла, DI, связного объектного контракта или полиморфизма.
Нельзя использовать такие конструкции только для уменьшения файла, группировки
функций или обхода проблемы типизации. Набор чистых правил должен оставаться
module-level функциями с явными зависимостями; скрытая связь mixin-методов через
members будущего subclass и `type: ignore[attr-defined]` запрещена.

Новые и изменяемые docstring, комментарии, TODO, FIXME и документация пишутся
на русском; английский оставляется только для неизбежных технических
идентификаторов и команд.

## 6. Тестовая стратегия

### Во время разработки

Сначала запускать ближайший тестовый файл или отдельный тест:

```powershell
.\.venv\Scripts\python.exe -m pytest tests\<area>\test_<feature>.py
.\.venv\Scripts\python.exe -m pytest tests\<area>\test_<feature>.py::test_<case>
```

Для исправления человеческих фраз минимальный набор включает:

- точную фразу из инцидента;
- 2–3 естественных перефразирования;
- текстовый и голосовой контракт, если маршрут общий;
- отрицание (`не добавлять`, `не надо`, и подобное);
- неоднозначную фразу, которая должна запросить уточнение;
- соседний сценарий, который раньше работал.

### Перед передачей результата

```powershell
.\.venv\Scripts\ruff.exe format --check src tests scripts alembic
.\.venv\Scripts\ruff.exe check src tests scripts alembic
.\.venv\Scripts\python.exe -m mypy src
.\.venv\Scripts\python.exe -m pytest
.\.venv\Scripts\python.exe scripts\generate_user_scenarios.py --check
.\.venv\Scripts\python.exe scripts\check_markdown_links.py
git diff --check
```

Если менялись модели SQLAlchemy или миграции:

```powershell
.\.venv\Scripts\alembic.exe heads
.\.venv\Scripts\alembic.exe check
```

Если менялись контейнерные контракты и это было явно разрешено:

```powershell
docker compose config --quiet
docker compose build api worker migrate
```

Полный набор можно уменьшить только с объяснением, почему пропущенная проверка не относится к изменению.

## 7. Пользовательские сценарии и UX

При изменении текста, кнопок или маршрута сначала правится `docs/user-scenarios/scenarios.json`, затем выполняется:

```powershell
.\.venv\Scripts\python.exe scripts\generate_user_scenarios.py
```

После генерации проверить `docs/USER_SCENARIOS.md`, автономный `docs/user-scenarios/index.html` и `tests/docs/test_user_scenarios.py`. Производные Markdown/HTML не должны расходиться с JSON.

Текст оценивается глазами повара:

- понятно, куда добавлены товары;
- понятно, что требуется сейчас;
- нет внутренних слов `state`, `intent`, `checkpoint`, `dispatch`;
- предупреждение объясняет последствие и следующий шаг;
- кнопки выражают действие, а не техническое состояние.

## 8. Локальная сборка

Обычная безопасная последовательность:

```powershell
docker compose up -d postgres redis
docker compose run --rm migrate
docker compose up -d --build api worker beat
docker compose ps
```

До тестирования проверить `/health/live`, `/health/ready` и свежие логи API/worker. Публичный Quick Tunnel и повторная регистрация webhook выполняются только по отдельному запросу. Смена URL требует согласования `PUBLIC_BASE_URL`, пересоздания нужных сервисов и `set-webhook`.

Локальная проверка не должна включать внешнюю отправку заявки. Текущее безопасное положение переключателя — `GOOGLE_ORDER_SUBMISSION_ENABLED=false`.

## 9. Подготовка commit и push

Commit или push выполняется только по запросу пользователя.

1. Обновить снимок: `python scripts/build_agent_context.py`.
2. Проверить `git status`, `git diff --stat`, `git diff --check` и каждый изменённый файл.
3. Убедиться, что в staging попадут только файлы текущей задачи.
4. Проверить отсутствие секретов, runtime-файлов, логов и тестовых артефактов.
5. Перед push выполнить `git fetch origin --prune`.
6. Текущая ветка декомпозиции — `decompose_bot`; перед push сравнить активную
   `decompose_bot`, `origin/decompose_bot` и общий base.
7. Не переключаться на `develop` и не выполнять автоматические merge или rebase
   с `develop`; переход на другую ветку возможен только по прямому указанию пользователя.
8. Не применять force push.
9. Commit писать по-русски от первого лица: `Поправил ...` или `Добавил ...`.
10. После push сравнить локальный и удалённый commit и проверить pipeline.

`manual_smoke_forensic_logs.txt` — необязательный локальный diagnostic artifact,
а не tracked-файл репозитория. Если он существует, его нельзя менять, удалять
или добавлять в commit; отсутствие файла нормально и не блокирует работу.

Документация не должна называть commit «текущим decomposition HEAD»: после
нового commit это сразу устаревает. Фиксируются только стабильные accepted
baseline SHA, а текущий HEAD проверяется командой `git rev-parse HEAD`.

DevOps-шаблоны не адаптируются «для удобства» без участия DevOps. Если pipeline сломан внутри подключённого корпоративного шаблона, сначала собрать доказательства и передать владельцу.

## 10. Инциденты и отказоустойчивость

При production-сбое:

1. Не повторять вручную потенциально выполненную отправку.
2. Проверить `telegram_updates`, `submission_records`, состояние сессии и структурированные логи.
3. Различать: update не принят, задача не взята, AI не ответил, state не сохранён, Telegram reply не доставлен, Google write не выполнен, результат внешней отправки неопределён.
4. При неопределённом результате после начала внешнего POST не выполнять автоматический повтор.
5. Исправление инцидента сопровождается тестом на повтор, timeout или частично выполненную контрольную точку.
