# Процесс разработки

Этот документ — исполнимый чек-лист. Архитектурные ограничения находятся в
`AGENTS.md`, владельцы модулей — в `PROJECT_MAP.md`, долговременные решения — в
`DECISIONS.md`.

## 1. Восстановить контекст

Из корня репозитория выполнить:

- `python scripts/build_agent_context.py`
- `Get-Content .agents\runtime\CURRENT_CONTEXT.md`
- `git status --short --branch`
- `git log -1 --oneline`

Затем прочитать `PROJECT_HANDOFF.md`, документы из `.agents/`, затронутый код,
его тесты и существующий diff. Не начинать исправление только по скриншоту, если
доступны код и логи.

## 2. Найти полный маршрут ошибки

| Сценарий | Обязательная цепочка проверки |
|---|---|
| Маршрутизация | Событие Telegram → нормализация → разбор/ИИ → координатор → механизм состояний → ответ |
| Товар | Исходная фраза → структура ИИ → каталог → варианты → состояние позиции |
| Количество/единица | Парсер → единицы → текущий вопрос → кратность → финальная проверка |
| Комментарий | Структура ИИ → локальная/общая область → источник комментария → строка заявки |
| Отправка | Проверка механизма состояний → ожидающая отправка → контрольные точки → Sheets → пересчёт → ответ |
| Статус | Привязка заведения → история без записи → группировка → постраничный вывод |
| Доступ | Центральный реестр → кэш → привязка заведения → повторная проверка перед эффектом |
| Инфраструктура | Сначала диагностика без записи по DevOps-контракту; изменение — только с разрешением |

Для инцидента зафиксировать время, `update_id` или хэш чата, вид входа, состояние
до и после перехода и ожидаемый результат. Проследить один update в узком окне
структурированных логов:

`вход → нормализация → разбор → сверка → маршрутизация → состояние → сохранение → внешний эффект`.

Исправлять первый подтверждённый неверный этап. Если он не доказан логом или
тестом, продолжать диагностику, а не добавлять новую защиту или резервный путь.
Не печатать окружение и секреты.

## 3. Спроектировать изменение

До кода сформулировать:

1. правило для пользователя простыми словами;
2. текущий неверный переход и владеющий модуль;
3. новый безопасный переход и допустимые изменения состояния;
4. похожие маршруты, которые нельзя изменить;
5. положительные, отрицательные и межканальные проверки.

ИИ нужен для понимания свободной речи. Доступ, навигация, отрицание, выбор,
количество, подтверждение и внешний эффект закрепляются детерминированным
контекстом и машиной состояний. Не подставлять похожий товар, не выбирать первую
позицию при неоднозначной голосовой цели и не связывать бизнес-правило с текстом
кнопки вместо её идентификатора.

Перед переносом, слиянием, разделением или удалением символа выполнить полный
аудит репозитория: вызывающие места в приложении и тестах, псевдонимы,
повторный экспорт, динамические вызовы фреймворка, похожие реализации и мёртвый
код. После переноса повторить проверку. Один инвариант имеет одного владельца;
фасад допустим только как простой повторный экспорт без алгоритма.

## 4. Реализовать

- Менять слой, где появилась причина, а не финальный текст карточки.
- Нормализовать данные один раз в явной границе; не дублировать словари фраз и
  постобработку без владельца.
- Новый параметр получает тип, валидацию, безопасное значение в `.env.example`,
  документацию и тест. Для БД — новую миграцию Alembic; существующие миграции не
  переписывать.
- Внешний эффект должен быть идемпотентным и повторно проверять доступ.
- Чистые правила оставлять функциями модуля с явными зависимостями. Класс,
  примесь или `Protocol` вводить только при настоящем объектном контракте или
  полиморфизме.
- Новые документирующие строки, комментарии, `TODO`/`FIXME` и документация — на
  русском; английский допустим только в идентификаторах и командах.

## 5. Проверить

Во время работы сначала запускать ближайший тест:

- `.\.venv\Scripts\python.exe -m pytest tests\<область>\test_<функция>.py`
- `.\.venv\Scripts\python.exe -m pytest tests\<область>\test_<функция>.py::test_<случай>`

Для изменения человеческой фразы проверить точную фразу, 2–3 естественных
перефразирования, текст и голос при общем маршруте, отрицание, неоднозначный
вариант и работавший соседний сценарий.

Перед передачей результата выполнить пропорционально риску:

- `.\.venv\Scripts\ruff.exe format --check src tests scripts alembic`
- `.\.venv\Scripts\ruff.exe check src tests scripts alembic`
- `.\.venv\Scripts\python.exe -m mypy src`
- `.\.venv\Scripts\python.exe -m pytest`
- `.\.venv\Scripts\python.exe scripts\generate_user_scenarios.py --check`
- `.\.venv\Scripts\python.exe scripts\check_markdown_links.py`
- `git diff --check`

Если менялись модели или миграции, выполнить `.\.venv\Scripts\alembic.exe heads`
и `.\.venv\Scripts\alembic.exe check`. Если по отдельному разрешению менялись
контейнерные контракты, выполнить `docker compose config --quiet` и
`docker compose build api worker migrate`.

Пропуск проверки объяснить: почему она не относится к изменению и что было
проверено вместо неё.

## 6. UX, локальный запуск и инциденты

При изменении текста, кнопки или маршрута сначала изменить
`docs/user-scenarios/scenarios.json`, затем выполнить
`python scripts/generate_user_scenarios.py`. Проверить сгенерированные
`docs/USER_SCENARIOS.md`, `docs/user-scenarios/index.html` и тесты документации.

Для локального запуска без внешней отправки:

- `docker compose up -d postgres redis`
- `docker compose run --rm migrate`
- `docker compose up -d --build api worker beat`
- `docker compose ps`

Проверить `/health/live`, `/health/ready` и свежие логи API и worker.
`GOOGLE_ORDER_SUBMISSION_ENABLED` остаётся `false`. Туннель и webhook — только
по отдельному запросу; смена URL требует обновления `PUBLIC_BASE_URL`, пересоздания
нужных сервисов и явного `set-webhook`.

При инциденте в боевом окружении не повторять вручную потенциально выполненную
отправку. Различить: update не принят, задача не взята, ИИ не ответил, состояние
не сохранено, ответ Telegram не доставлен, запись в Sheets не выполнена или
внешний результат неопределён. Неизвестный исход начатого внешнего POST не
повторять автоматически; добавить тест на повтор, таймаут или частичную
контрольную точку.

## 7. Фиксация изменений и завершение

Фиксация изменений и отправка в удалённый репозиторий — только по прямому запросу
пользователя.

1. Обновить `python scripts/build_agent_context.py`.
2. Проверить `git status`, `git diff --stat`, `git diff --check` и каждый файл.
3. В индекс Git добавить только текущую задачу; исключить секреты, файлы среды
   выполнения, логи и тестовые артефакты.
4. Выполнить `git fetch origin --prune`, проверить активную и удалённую ветки.
5. Не выполнять автоматическое слияние или перебазирование, не применять
   принудительную отправку.
6. После отправки сверить `HEAD` с удалённой веткой и проверить конвейер CI.

При завершении обновить `PROJECT_HANDOFF.md`, если изменился код, тесты,
архитектурное решение, проверенное поведение или известный риск. Сообщить
пользователю причину, изменённые файлы и владельца, проверки, невыполненные
внешние действия и оставшиеся ручные шаги.
